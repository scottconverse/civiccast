## Verify and install

Check the installer's hash and signature before you run it:

```powershell
Get-FileHash 'CivicCast (Native)_1.0.0-rc.5_x64-setup.exe' -Algorithm SHA256
Get-AuthenticodeSignature 'CivicCast (Native)_1.0.0-rc.5_x64-setup.exe' | Format-List Status, SignerCertificate, TimeStamperCertificate
```

You should see the SHA-256 listed above, `Status` Valid, signer `CN=Scott Converse`, and a Microsoft timestamp. If anything differs, stop. Then follow the [Windows installation guide](https://github.com/scottconverse/civiccast-native/blob/main/INSTALL-WINDOWS.md) and the [release-trust guide](https://github.com/scottconverse/civiccast-native/blob/main/docs/install/windows-release-trust.md).

- Run setup at the station computer itself, not over a remote shell.
- Upgrading from rc.4: back up the station and leave disk headroom. Do not uninstall first; setup upgrades in place and keeps your data.
- If an upgrade fails, setup restores the previous station. Keep the installer log and don't retry blindly.

## What changed since rc.4

**Live captions while programmes are prepared (FT-7)**

The station prepares each upcoming programme on the same processor that runs live captions. On the Beelink target station, captions lost that contest: during background preparation they were dropped or ran 20–33 s late, and at programme changes they averaged 14.7 s with 100 words over 10 s. Three causes were measured:

1. Background preparation ran at the same Windows priority as captions, with many more threads.
2. Some PCs, the Beelink among them, have no hardware H.264 encoder. Windows' software encoder spreads across every core and ignores CivicCast's one-thread setting, so a lower priority alone wasn't enough.
3. At each programme change, on-the-spot preparation ran above captions in priority, on every core.

rc.5 runs the station's work in a strict order:

| Priority | Work | Cores |
|---|---|---|
| Above Normal | playout encoders (unchanged) | all |
| Normal | control plane and the live caption engine | all |
| Below Normal | on-the-spot preparation | lower half |
| Idle | background preparation | top quarter (on PCs with 4 or more cores) |

A background preparation held to 4 cores still ran at 12.3× real time on the Beelink, well inside its time limit.

**Security: FFmpeg advisories of November 6, 2026**

- Six advisories were published against the three FFmpeg builds CivicCast ships.
- Five (G2M, PCX, Sun Raster, CDXL and Huffyuv decoders) were already fixed in the bundled FFmpeg source, or aren't built into the two smaller copies. Each is recorded in `security/native-audit-triage.json`.
- One was real: FFmpeg's IMF package reader (CVE-2026-120210) can be made to open files outside a crafted package. Uploads, watch-folder imports and contributions now refuse XML documents before FFmpeg opens them, and the operator override cannot bypass this. On rc.4, an IMF package named like a video file was accepted under that override.

**A failed programme change no longer leaves a channel on the slate for half an hour (FT-8)**

Found on a Ryzen 7 field station running rc.4, November 6, 2026. The public channel repeats a 90-second programme, so it prepares a programme change every 90 seconds. At 09:02 one of those preparations failed:

1. The programme's start offset had drifted to 0.000056 s. CivicCast wrote it for FFmpeg as `5.6e-05` (scientific notation), and FFmpeg rejected it.
2. After a failed preparation the station waited for the outgoing programme to end and the worker to exit. Since an earlier fix (U41), the worker no longer exits at a programme's end: it holds the slate. So nothing restarted the channel, and the regular slate retry didn't apply because the channel reported "transitioning".
3. Only the stall watchdog recovered it, after its fixed 27.5-minute limit. The public channel aired the slate from 09:04:15 to 09:30:46.

rc.5 fixes both:

- Every FFmpeg start offset and duration is written as a plain decimal at microsecond precision. The old format also rounded long offsets to six digits, for example 74,564.970002 s to 74,565 s.
- When a programme change fails to prepare, the station retries it one minute after the outgoing programme ends, instead of after 27.5 minutes. It never retries before that end, so a bad next programme can't cut a healthy one short. Other stalls keep the 27.5-minute watchdog.

This was very likely also the cause of the earlier field report FT-6 (a channel on the slate that started its programme only after a manual reload).

## Known issues

- **IMF through live network sources:** a staff-configured live network source (SRT, HLS or MPEG-TS) whose remote sender serves a crafted IMF package is not covered by the intake refusal. Only add network sources you trust. The bundled FFmpeg will be updated once upstream merges its fix (FFmpeg pull 25341); this entry is reviewed again on November 20, 2026.
- **Upgrades take the station off the air:** about 13 minutes in the field rc.3 → rc.4 upgrade. Schedule the upgrade outside meetings and programs.
- **Web-stream errors right after an upgrade:** in the first minute after the upgraded service starts, the station can log one ERROR per channel ("HLS relay child … has never written a live window … Attempting a bounded relay self-heal."). It repairs this by itself within a few minutes. Check that each channel's web preview plays a few minutes after setup.
- **Channels screen can stay out of date after a preset:** after **Enable web preview** succeeds, the Channels screen can keep saying "No outgoing-feed configuration…" until you reload the browser page.
- **Scripts that sign in on every API call sign staff out:** the station limits concurrent console sessions and removes the oldest one. Integration scripts should sign in once and reuse the session token.
- **Captions are machine-generated:** delay is measured, but accuracy is not calibrated against human transcripts. At a programme change, a caption page still being spoken can be cut off, so old text never carries into the next programme.
- **Captions slow down if the station PC is busy with programs other than CivicCast:** rc.5 orders CivicCast's own work so captions come first, but it can't control other programs. Run the station on a PC that isn't doing other heavy work.
- **Uninstall leftovers:** `C:\Program Files\CivicCast (Native)\uninstall.exe`, and the service-account profile folder `C:\Windows\ServiceProfiles\CivicCastSupervisor` (Windows holds it open; it contains one Windows credential-store file).
- **Gate A sandbox:** the automated Windows Sandbox acceptance run freezes inside the sandbox, so it gives no verdict. This is a test-harness problem; acceptance runs on real machines instead.
- **Bundled AI runtime advisory:** GO-2026-6860 (High) in the Go `golang.org/x/net` 0.61.0 library built into the bundled `ollama.exe`. CivicCast's Ollama listens only on 127.0.0.1 and receives input only from the station. It will be fixed when an Ollama build with x/net 0.62.0 is bundled.
- **Platform:** Windows 11 is the verified platform; Windows 10 and Windows Server are not verified. No minimum hardware specification is certified for three channels.

## What changed since rc.5

**Cable output: AC-3 sound and a constant bit rate (#324, #325, #326)**

Found on a clean rc.5 test station on November 12, 2026.

- On rc.5, every cable preset set AC-3 as the sound for the whole channel. The FFmpeg build bundled for the default GStreamer playout engine had AC-3 switched off, so the channel never went on air. The health page still said "healthy".
- The preset's bit-rate setting (`-muxrate`) was not read by that engine. The cable feed was variable: 274 kb/s measured against the 8 Mb/s the preset asks for.

rc.6:

- The bundled FFmpeg build includes the AC-3 encoder and decoder.
- A cable preset puts AC-3 on the cable output only. The channel and its web output stay AAC, which browsers, phones and TV apps play.
- The cable output is padded to the preset's constant bit rate.
- Saving AC-3 sound or MPEG-2 video as the channel codec is refused with a plain reason.
- The `comcast-mtd-sd` preset asks for MPEG-2 video, which this engine does not make. The preset keeps H.264 and says so on the screen.

Why AC-3 on cable: SCTE 54 (2009) section 5.3 requires a complete main AC-3 audio service, with stream type 0x81 and the `AC-3` registration descriptor.

**Upgrade repair for stations that already applied a cable preset (#327, #328)**

A station that applied a cable preset on rc.5 or earlier has AC-3 saved on the channel. At service start, rc.6 moves that saved setting once: the channel goes back to AAC (and H.264), and each cable output keeps AC-3. The change is written to the log. No operator step is needed.

**The element cache follows the FFmpeg files (#326)**

GStreamer keeps a cache of the elements it can use. An upgrade that kept the old cache hid the new AC-3 elements (measured on the test station). The cache file is now named after the FFmpeg files' contents, so a changed FFmpeg always gets a fresh cache.

**AI meeting summaries from Gemma 4 (#314)**

Summaries are no longer thrown out for reasons unrelated to their evidence. The request sizes the model's context to the whole transcript and switches Gemma 4's hidden reasoning off. Meetings too long for one pass (about 80 minutes) are refused before the model loads, with a plain reason. On seven Longmont meetings, gemma4:12b went from 0 of 5 summaries reaching review to 5 of 5.

**Also in this candidate**

- False "degraded" health blips for live captions are fixed (#313).
- Agenda import reads meetings through the shared Townlight reader (#315).
- The bundled Python 3.12.16 runtime archive was built again from the same pinned sources (#320). The standard library is byte-identical; the 27 compiled files are a new compile of the same source.
- The repository is now `scottconverse/civiccast`; docs and the download helper point to it.
- Test-only: a test that leaks a database connection now fails (#323). The unused Gate B reboot lane was removed (#322).

## Known issues

- **No real cable headend has received this feed.** The cable checks are ffprobe, TSDuck and the product's compliance probe.
- **AC-3 loudness tag (dialnorm):** the AC-3 encoder's default value is used. It is not set from the channel's loudness target.
- **Cable clock reference:** in the cable output the PCR is carried on the audio stream.
- **MPEG-2 video is not available on the default playout engine.** The `comcast-mtd-sd` preset sends H.264.
- **Health during a worker restart loop (#327):** if a playout worker restarts again and again, the health page can still say "healthy".
- **YouTube Live from the Publish page** (the Google sign-in path) was not tested on this candidate.
- **Old element cache files are not removed** after an upgrade. They are small.
- The rc.5 known issues that this candidate does not change still apply; see the [RC5 release notes](v1.0.0-rc.5-release-notes.md#known-issues).
